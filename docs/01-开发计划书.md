## 1.项目概要

### 1.1 项目名

**校园二手拍卖与即时通讯平台**（Campus Auction & IM Platform, 简称 CAIP）

### 1.2 开发目的和背景

#### 背景
高校校园每年毕业季和开学季产生大量二手物品交易需求。现有交易渠道（QQ群、微信群、校园墙）存在以下问题：
- **信息混乱**：消息刷屏严重，商品信息难以检索和追溯
- **价格不透明**：买卖双方反复议价效率低，缺乏公允的价格发现机制
- **交易无保障**：先款后货存在信任风险，缺乏信誉评价体系
- **沟通碎片化**：交易咨询混在群聊中，买卖双方难以高效沟通

#### 目的
构建一个面向高校学生的二手交易平台，以**实时拍卖**为核心交易模式解决价格发现问题，以**内置即时通讯**替代群聊碎片化沟通，以**信誉评价体系**降低交易风险。同时，该系统作为软件工程实验课项目，完整实践需求分析→系统设计→编码实现→测试交付的全流程。

#### 可行性
- **技术可行性**：Spring Boot + Vue 3 + WebSocket + PostgreSQL，均为成熟技术栈
- **经济可行性**：开源技术栈无需付费授权，部署于学校服务器或云主机
- **时间可行性**：6人团队4周开发，功能范围可控

### 1.3 功能概要

本平台包含**6大功能模块**：

| 模块编号 | 模块名称 | 功能概要 |
|:--------:|---------|---------|
| M1 | 用户与认证 | 注册登录（学号+邮箱验证）、JWT认证、个人信息管理、实名认证 |
| M2 | 商品发布与搜索 | 商品发布（多图+描述+分类+起拍价）、全文搜索、多条件筛选、商品收藏 |
| M3 | 实时拍卖引擎 | 英式拍卖（升价竞拍）、出价记录实时推送、倒计时自动成交、荷兰式拍卖（降价）可选 |
| M4 | 即时通讯(IM) | 买家卖家1对1私聊、消息已读/未读、聊天记录持久化、消息推送通知 |
| M5 | 订单与交易 | 成交后订单创建、交易状态流转（待付款→已发货→已收货→已完成）、模拟支付 |
| M6 | 信誉与统计 | 用户信誉评分、交易评价、个人主页（成交数/好评率）、平台数据统计看板 |

**系统整体业务流程：**
```
用户注册 → 发布商品(设置起拍价+拍卖时长) → 买家浏览/搜索商品
  → 参与竞拍(实时出价) → 拍卖结束自动成交
  → IM沟通细节 → 下单支付(模拟) → 发货/收货 → 互相评价
```

### 1.4 作业范围

- **本团队承担范围**：全部6个模块的设计、编码、测试、部署
- **不涉及的部分**：
  - 真实支付对接（使用模拟支付）
  - 短信/邮件服务（使用站内通知代替）
  - 移动端App（仅Web端，移动端浏览器适配）
  - AI推荐算法（使用简单的协同过滤或热门推荐）

### 5.2 开发模型

采用**增量模型 + 敏捷开发**混合模式：
- 整体按增量模型：先交付核心功能(M1+M2+M3) → 再交付完整功能(M4+M5+M6)
- 日常按敏捷开发：每周为一个Sprint，周初分配任务，周末回顾

**开发阶段划分：**
```
Phase 1 (第1周)：核心功能
  ├── 项目脚手架搭建 + 数据库初始化
  ├── M1 用户与认证（注册+登录+JWT）
  ├── M2 商品发布与搜索（发布+列表+搜索）
  └── M3 拍卖引擎（创建拍卖+出价+成交）

Phase 2 (第2-3周)：完整功能
  ├── M4 即时通讯（私聊+消息推送）
  ├── M5 订单与交易（订单流程+支付模拟）
  └── M6 信誉与统计（评价+统计看板）

Phase 3 (第4周)：测试+部署+文档
  ├── 集成测试 + 性能测试
  ├── Docker部署验证
  └── 文档整合 + 答辩准备
```

采用**测试金字塔**模型：

```
        /\
       /E2E\          ← Playwright (2-3个核心用户旅程)
      /------\
     / 集成测试 \       ← JUnit + Testcontainers (全部API)
    /----------\
   /   单元测试   \     ← JUnit5 + Mockito (覆盖率 ≥ 70%)
  /--------------\
```

- **单元测试**：每个Service/Mapper方法，Mock外部依赖

- **E2E测试**：注册→浏览商品→出价→成交→评价，完整流程

## 11.风险管理

### 11.1 风险识别与应对

| 编号 | 风险描述 | 发生可能性 | 影响范围及程度 | 预防方法 | 应对策略 |
|:--:|---------|:-------:|--------------|---------|---------|
| R1 | **WebSocket实时推送实现困难**：拍卖出价并发场景下消息丢失或延迟高 | 中 | 高：拍卖模块核心体验，影响M3和M4 | 早期搭建WebSocket原型验证可行性；使用STOMP协议简化开发 | 降低实时性要求（如手动刷新作为降级方案）；组内技术讨论+请教助教 |
| R2 | **数据库全文搜索性能差**：PostgreSQL GIN索引搜索中文分词效果不佳 | 中 | 中：搜索体验不好但可降级为LIKE查询 | 提前测试PG全文检索中文效果；准备zhparser中文分词插件 | 降级为`ILIKE`模糊搜索 + 分类筛选，放弃全文检索 |
| R3 | **成员进度不一致**：某个模块延期阻塞依赖模块 | 高 | 高：影响整体进度，可能导致无法按时交付 | 每日站会暴露问题；功能分支并行开发减少依赖；复杂模块提前启动 | 组长协调资源倾斜；必要时缩小延期模块的功能范围 |
| R4 | **拍卖并发冲突导致数据不一致**：同一时刻多用户出价，价格记录错乱 | 中 | 高：拍卖核心逻辑错误将严重影响评分 | 使用Redis Lua脚本原子操作出价；数据库乐观锁防并发 | 增加出价冲突测试用例；压测验证 |
| R5 | **团队对WebSocket/STOMP不熟悉**：学习成本高，开发效率低 | 中 | 中：M3和M4开发效率下降 | 提前在第1周安排WebSocket学习；准备Demo参考代码 | 寻求助教帮助；参考开源IM项目代码 |

```
main ← dev ← feat/<module-name>
```

| 分支 | 用途 | 保护规则 |
|------|------|---------|
| `main` | 最终交付版本 | 禁止直接push，仅从dev合并 |
| `dev` | 开发集成 | 禁止直接push，通过PR合并 |
| `feat/user-auth` | M1 用户认证 | 成员1维护 |
| `feat/product-search` | M2 商品搜索 | 成员2维护 |
| `feat/auction-engine` | M3 拍卖引擎 | 组长维护 |
| `feat/chat-im` | M4 即时通讯 | 成员3维护 |
| `feat/order-trade` | M5 订单交易 | 成员4维护 |
| `feat/review-stats` | M6 信誉统计 | 成员5维护 |

### 12.3 提交信息规范

采用 **Conventional Commits** 格式：

```
<type>(<scope>): <description>

示例：
feat(auction): 实现拍卖出价WebSocket实时推送
fix(user): 修复JWT Token过期后登录状态丢失问题
docs(plan): 完善开发计划书风险管理章节
test(order): 添加订单状态流转单元测试
refactor(product): 优化商品搜索SQL查询性能
```

| Type | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug修复 |
| `docs` | 文档变更 |
| `refactor` | 代码重构 |
| `test` | 测试相关 |
| `style` | 代码格式 |
| `chore` | 构建/工具 |

### 12.4 禁止事项

- ❌ 禁止直接push到main或dev
- ❌ 禁止force push
- ❌ 禁止提交包含密码/密钥/Token的代码
- ❌ 禁止提交node_modules/、target/、.env
- ❌ 禁止未经过代码审查直接合并PR
